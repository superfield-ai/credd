## Executive Summary

credd is in **early design phase** — the repository contains comprehensive threat modeling and architectural design documents (README, PRD, DESIGN.md) but only skeleton crate stubs with no implementation. The architecture on paper is strong: a clean privilege separation between a sealed core and disposable stateless guards, tiered secret classification with cryptographic enforcement, and a coherent threat model that acknowledges same-UID attacks rather than pretending to prevent them. This review evaluates the *design* against the stated goals and identifies gaps that must be addressed before implementation.

---

## Strengths

### 1. Honest Threat Model (DESIGN.md § Threat Model / Attack Vectors and Defenses)
The design explicitly acknowledges that same-UID attackers cannot be fully contained on developer machines and builds controls around that reality (short TTLs, attribution, audit, revocation) rather than claiming isolation that doesn't exist. This is rare and correct.

### 2. Clean Privilege Separation — No JSON Parser for Untrusted Input
The core/guard split with Unix socket IPC, dedicated UIDs, seccomp, and netns egress allowlists creates a real compromise boundary. Guard RCE = bounded lease exposure, not root key loss. The core has no JSON parser for untrusted input over its length-prefixed Unix socket (README § Architecture; DESIGN.md § Architecture: Sealed Core, Disposable Guards) — policy is signed YAML and is parsed only after Ed25519 signature verification (DESIGN.md § Multisig for Critical Operations / § Policy, plugin, and supply-chain tampering), so the "no JSON parser" property holds narrowly for the untrusted data path.

### 3. Tiered Secrets with Cryptographic Enforcement
Three tiers (Local/Leased/Ceremonial) with distinct access rules, enforced by envelope AEAD + KEK sealing + Shamir-split Tier 2 KEK. Tier 1 derivatives never expose roots; Tier 2 requires M-of-N hardware signatures. This maps cleanly to the threat model.

### 4. Audit Chain with WORM Sink
Ed25519-signed hash chain shipped to append-only storage in a separate account. Gaps are detectable. Shipping interval in seconds limits residual exposure.

### 5. Wire Injection Default
Execution proxy prefers HTTPS_PROXY + per-run CA over in-process injection, with namespace isolation and `weak_path=true` audit tagging for the fallback path. This directly addresses the "child process leaks secrets via debug logs/env" vector.

## Critical Gaps & Risks

### 1. No Implementation Exists
All crates are empty stubs. The design is unvalidated by code. **Risk**: Implementation will reveal constraints not captured in design (e.g., pidfd portability, TPM/Enclave/KMS abstraction complexity, cross-platform Unix socket framing).

### 2. Approval Routing Underspecified (DESIGN.md Note 1; DESIGN.md § Multisig for Critical Operations)
DESIGN.md Note 1 and § Multisig for Critical Operations already state the core replay/expiry properties: "executes once, then burns the nonce" and "Signatures bind to the exact request bytes and carry an expiry." So the gap is not "no spec" but underspecified. "Pluggable notifier (Slack, PagerDuty, or CLI inbox)" with "diff rather than summary" for reviewers is described, but still missing:
- Request serialization format for signing (canonical bytes)
- Nonce lifecycle details and replay protection across approvers (burn semantics are stated, cross-approver coordination is not)
- Approver key enrollment/rotation ceremony
- Timeout/expire semantics for pending approvals beyond "time-boxed" / "carry an expiry"
- What happens if quorum is unreachable (freeze vs. degrade)

This is the **primary human-in-the-loop control** for Tier 2 and policy — it should be tightened via ADR before Tier-2-gated core paths (policy load, Tier-2 unseal) are implemented, though it does not block early protocol/peercred/audit work.

### 3. SPIFFE/mTLS Production Path Undefined (DESIGN.md § Attack Vectors and Defenses — 02 Caller impersonation)
DESIGN.md § Attack Vectors and Defenses — 02 Caller impersonation states production uses SPIFFE SVIDs over mTLS, but on main at b8e587c:
- No crate for SPIFFE integration (spiffe-rs? workload API?)
- No certificate rotation design (hourly rotation mentioned, but how?)
- No trust root distribution mechanism
- No cross-zone core synchronization design ("two cores per zone against shared sealed store on KMS")

> Note: Vendor selection (SPIFFE Rust `spiffe` + `rustls`/`tokio-rustls` with `x509-parser`, hourly-rotated SVIDs) exists in concurrent unmerged architecture work (`adhoc/20260918-193242-architecture` `docs/architecture.md` § Vendor Selections) but is not on `main` at b8e587c. Gap remains valid for `main`; concurrent work should be merged or referenced rather than re-decided.

### 4. Lease Minting & Derivation Logic Unspecified
PRD §5 "Secret Retrieval via Proxy" says "mints a short-lived derivative credential." DESIGN.md § Secret Tiers says "credd-core mints the derivative; root never leaves store." But:
- What derivative types? (AWS STS session, GCP impersonation token, GitHub App token, SSH cert, DB password, generic HMAC key?)
- Each vendor has different API, TTL semantics, and scope model.
- No abstraction layer defined. This will be the largest surface area in guards.

### 5. Policy Language & Evaluation Undefined
`credd-policy` crate is empty. Need:
- Principal matching (SPIFFE ID, executable hash, cgroup, UID)
- Path glob semantics with tier awareness
- Rate limiting / anomaly detection thresholds
- Policy versioning and signed document format
- Quorum-gated mutation rules

### 6. Seal/Unseal Ceremony Unspecified
PRD §5 "Bootstrapping and Recovery" mentions "strict multi-party cryptographic ceremonies for production initialization" and "single-admin config for testing with warnings." No details on:
- Initial KEK generation and sealing to TPM/Enclave/KMS
- Shamir split ceremony for Tier 2 KEK
- Disaster recovery: quorum loss, KMS unavailability, TPM failure
- Migration between seal backends

### 7. Cross-Platform Guard Isolation Gaps
- Linux: seccomp, netns, pidfd, hidepid — well-defined.
- macOS: "launchd daemon under separate UID", "hardened runtime, no get-task-allow". No seatbelt profile, no network extension for egress allowlist, no pidfd equivalent (uses LOCAL_PEERCRED only). The isolation story is weaker on macOS — should be documented as a known limitation.

### 8. Leak Monitor Coverage Gaps (DESIGN.md § Guards — Leak monitor)
DESIGN.md § Guards — Leak monitor: monitor watches "git hooks, execution proxy, shell history, clipboard."
- Misses: container logs (docker/podman), Kubernetes pod logs, CI job logs, editor swap files, tmux/screen capture, browser devtools, VS Code extension host.
- "Out-of-band log tailing" — no spec for log source plugins, cursor persistence, rotation handling, or backpressure.

> Wording note: `crates/scanner/src/lib.rs:1-5` comment "Egress scanning / Blocks rather than redacts" is imprecise wording versus PRD Out of Scope ("inline egress scanning" and "silent redaction" are out of scope) — not a design drift. The actual design correctly does out-of-band scanning and revokes rather than silently redacting (DESIGN.md § Attack Vectors and Defenses — 06 Exfiltration through the model); the scanner crate comment should be reworded for precision.

### 9. No Secret Rotation Automation for Tier 1
DESIGN.md § Multisig for Critical Operations: "Tier 1 rotation does not need quorum: one human, plus a canary request against the new credential before the old one is revoked." But:
- No automated rotation scheduler
- No canary validation framework
- No overlap period management
- No integration with vendor rotation APIs (AWS IAM, GCP IAM, GitHub, etc.)

### 10. Binary Verification & Supply Chain
DESIGN.md § Policy, plugin, and supply-chain tampering (Attack Vectors and Defenses — 08) mentions "TUF-style metadata" and "reproducible builds" but:
- No build pipeline defined
- No sigstore/cosign integration
- No SBOM generation
- Plugin verification at load time — what plugin interface? Dynamic loading?

### 11. Zero-External-Deps Tension — WORM Sink & KMS (README vs DESIGN.md § Audit and Availability / § Secrets at rest)
README front-matter claims "zero external service dependencies" / "single binary," while DESIGN.md § Audit and Availability requires a WORM object sink "in a separate cloud account" (plus verifier job) and § Secrets at rest requires KEK sealing to TPM/Secure Enclave/cloud KMS. Keep as tension to reconcile, not contradiction: document that the "zero dependencies" property is the dev/single-host mode (local file sink + OS keychain/software KEK) and that production hardens by adding optional platform-native dependencies (separate-account WORM, KMS) — clarify PRD Constraints wording to distinguish "no required SaaS/DB cluster" from "no platform/operator-provided storage/KMS."

## Architectural Decisions Needed Before Implementation

| Decision | Impact | Recommendation |
|----------|--------|----------------|
| Derivative credential abstraction | Entire guard surface area | Define trait + 2-3 reference implementations (AWS STS, GitHub App, SSH cert) before core |
| Approval protocol wire format | Tier 2 + policy gate | Specify request object, nonce, expiry, signature aggregation (FROST vs. independent Ed25519) |
| SPIFFE integration strategy | Production viability | Candidate `spiffe` + `rustls`/`tokio-rustls` already in `adhoc/20260918-193242-architecture` (not on `main`); confirm and define SVID lifecycle / trust-root distribution |
| Policy language | All authorization | Start minimal: path glob + principal matcher + tier gate; add rate limits later |
| Cross-platform guard parity | Dev machine adoption | Document macOS limitations explicitly; consider user-mode Linux VM for parity |
| Seal backend abstraction | Portability | Define `SealBackend` trait with TPM, Enclave, KMS implementations |

## Test Coverage Policy Compliance (skills/_shared/test-coverage-policy.md)

The design mandates runtime behavior that **must** have executed-in-CI assertions:
- Guard compromise boundary (seccomp/netns/UID separation)
- Lease minting with correct TTL and attribution
- Audit chain signing + hash chaining + WORM shipping
- Quorum verification with hardware-backed signatures
- Wire injection vs. in-process fallback paths
- Leak detector normalization + revocation trigger

**Current state**: Zero tests. Implementation must use `#[ignore]` only for external resource dependencies (TPM, KMS, HSM), never for core logic. "No tests collected" must fail CI.

## Recommendations

### Immediate (Before Any Implementation)
1. **Specify approval protocol (ADR)** — request canonical bytes, nonce burn semantics, signature scheme (FROST vs. independent Ed25519), approver enrollment/rotation, timeout/expiry semantics, quorum-unreachable behavior. Note: nonce/expiry are already stated in DESIGN.md § Multisig for Critical Operations; ADR should tighten remaining enrollment/timeout/coordination details — blocks only Tier-2-gated core paths (policy load, Tier-2 unseal), not early infra.
2. **Define derivative credential trait (ADR)** — at least 2 vendor implementations (e.g., AWS STS, GitHub App) to validate abstraction before guard implementation; does not block `credd-protocol`/`peercred`/`audit` core infra.
3. **Design SPIFFE integration** — candidate already identified in concurrent architecture work (`spiffe` + `rustls`/`tokio-rustls`, hourly SVID rotation; `adhoc/20260918-193242-architecture`); confirm, define SVID lifecycle and trust-root distribution. Production feature — should not block MVP.
4. **Document macOS guard limitations** — explicit parity matrix vs. Linux (seatbelt, net extension, LOCAL_PEERCRED-only).

### Near-Term (Early Implementation — MVP-first)
5. Implement `credd-protocol` first — frame format, message types, versioning.
6. Implement `credd-peercred` with pidfd + executable hash pinning; add macOS fallback.
7. Implement `credd-audit` hash chain + signing; add WORM sink trait + local file + S3 implementations.
8. **Spike `exec-proxy` lease-mint + wire injection** — early validation of the primary workflow (mint derivative → inject via HTTPS_PROXY + per-run CA → attribute and audit with `weak_path` tagging). This is the MVP spine; should precede full policy/seal hardening.
9. Implement `credd-policy` minimal: tier-gated path glob + principal match + signed document (production hardening; can follow MVP spike).
10. Implement core seal/unseal with one backend (software KEK for dev, TPM for CI) — production KMS/Shamir split follows MVP.

> Sequencing note: `peercred`/`protocol`/`audit` and the `exec-proxy` spike are unblocked immediately. Only Tier-2-gated core paths (policy load, Tier-2 unseal) should wait for the approval-protocol ADR; derivative trait ADR should precede guard implementation, not core infra. SPIFFE/policy/seal are production features that should not block MVP validation.

### Deferred (Post-MVP)
11. Full leak monitor with plugin architecture for log sources.
12. Automated Tier 1 rotation with canary framework.
13. TUF-style plugin verification + reproducible builds.
14. Cross-zone core synchronization (shared KMS store).

## Conclusion

The architecture is **well-conceived and threat-model-driven** — a significant improvement over the typical "Vault-lite" designs that ignore same-UID attacks and audit tampering. The core/guard split, tiered secrets, and wire injection default are correct choices.

**However, the design has critical underspecified areas** (approval protocol, derivative abstraction, SPIFFE, policy language, seal ceremony) that will block implementation if not resolved first. `credd-protocol`/`peercred`/`audit` and an `exec-proxy` lease-mint spike are unblocked immediately; only Tier-2-gated core paths (policy load, Tier-2 unseal) should wait for the approval-protocol ADR, and the derivative-trait ADR should precede guard implementation rather than core infra — not a blanket "no core implementation" gate.

Recommend: Treat this as a **design validation phase**. Produce 3-4 focused ADRs for the underspecified areas (approval protocol, derivative trait, SPIFFE selection, policy language/seal), then implement protocol → peercred → audit → exec-proxy spike (wire injection + derivative + audit) → policy → core seal/unseal in that order, with executable tests at each layer. SPIFFE/policy/seal are production hardening that should not block MVP validation.
